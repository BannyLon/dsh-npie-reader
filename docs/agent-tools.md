# Agent 能力与数据语义

> 插件向 Harness 暴露的工具、参数语义，以及内置目录的取舍。

---

这个插件的定位不只是「人读」，而是**让模型替你读完**。所以除了界面，它把同一批数据
以工具的形式交给 agent：

| 工具 | 干什么 |
| --- | --- |
| `rss_list_channels` | 有哪些源（含未读数、最近一次抓取时间） |
| `rss_digest` | **一次调用**拿到「这几份源 + 这段时间」的简报清单，按源分组，每组给出条数与未读数 —— 一眼看出「哪份源这几天没说话」 |
| `rss_list_articles` | 某份源的文章列表，**可带时间窗**（`3d` / `72h` / `2w` / `2026-10-05`） |
| `rss_search_articles` | **全文检索**（标题 / 中文标题 / 摘要 / 正文），可用 `channels` 限定范围、用时间窗限定时间 |
| `rss_read_article` | 读一篇全文（原文 / 译文 / 改写） |
| `rss_generate_version` | 用本机模型补一份中文版本 |
| `rss_add_subscription` / `rss_remove_subscription` / `rss_refresh` | 订阅增删与刷新 |

于是「帮我分析最近 3 天技术圈对 DeepSeek-V3 的评估，只看我订阅的那几份 Newsletter」
变成一条干净的调用链：`rss_list_channels` → `rss_digest`（或 `rss_search_articles`）→ `rss_read_article`。

### 让 agent 读电子书（`book_*`，0.20.0）

逐章解读产出的 JSON 如果只有人能点开面板看到，那模型永远读不到 —— 所以同一批数据
也以 6 个工具的形式交出去：

| 工具 | 干什么 | 关键约束 |
| --- | --- | --- |
| `book_list` | 哪些书有解读 + 进度（已解读 / 略过 / 失败 / 待生成） | 「**正在生成中**」必须给出来，否则 agent 看到「0 章已解读」会建议用户再点一次 |
| `book_outline` | 章节树 + 每章状态、页码、实际用的模型 | 先调它，才知道哪几章真的有解读 |
| `book_chapter` | 读**一章** | 默认给**解读**（~1k token），`raw: true` 才给原文（~10 倍） |
| `book_search` | 在**解读**里检索（可跨书） | 中文按**子串**匹配不分词；一章只报第一处命中；触顶要说「可能不全」 |
| `book_annotations` | 读**你自己划的线 + 写的笔记** | **只读**（参数里没有任何写入口）；按页分组；不带 `bookId` 时跨书，但每本至少给一条 |
| `book_export_skill` | 把一本书导出成 skill 包 | 默认**不调模型**；`synthesize: true` 才多一次调用 |

- ★ `book_annotations` 读的是**你亲手标的东西**，不是模型写的摘要。两者在上下文里的分量
  不同：划线回答「他关心什么」，解读回答「这本书讲了什么」。所以工具会把这段文字明确
  标成 "the user personally highlighted"，并禁止模型把它说成书里的原话。
- ★ 它**不要求这本书有解读** —— 划线比解读出现得早，一本还没生成解读的书照样能读划线。
  这也是「不带 `bookId` 跨书汇总」的用处：`book_list` 只列有解读的书，划线不在那里面。
- ★ `book_chapter` 的输出**自己说明**「这一章是解读（不是原文）」。模型拿到一段通顺的
  中文时会默认它是原文，于是把一句概括当成作者的原话引用出去 —— 用户完全没法从输出里
  看出它被转过一手。
- ★ 原文封顶 20000 字，并**明说截断了多少**。悄悄截断会让模型把「后面没给」读成
  「后面没有」，于是替一本书的后半段下结论。
- ★ 检索的是**解读**而不是原文：解读本来就是「这本书关于 X 说了什么」的压缩形式，用它
  做索引能把「哪几章值得细看」的成本从「读整本」降到「读几千字」；要原话再 `book_chapter`。
- ★ 默认给解读而不是原文，是这条工具的价值所在：一页原文约 1500 字、一章上万字，
  而解读一章约 1k token —— 查询成本才和答案成正比，而不是每次都把整本书塞进上下文。

### 让 agent 记日记（`diary_*`，0.30.0；0.36.0 起可改可删）

日记是**用户自己写的**。0.30.0 上线时只有三个工具，而且是**故意单向**的：只有追加，
没有改写、没有删除 —— 理由是模型顺手「润色一下原文」就把那份「当时」擦掉了，
而用户多半不会逐字回读去发现。

★ **0.36.0 按用户的明确要求改了口径**（原话：「不能改也不能删。我需要的是能改能删」）。
所以现在是**五个**工具，「只追加」不再是产品规则，而是 **`diary_append` 这一个工具的行为**：

| 工具 | 干什么 | 关键约束 |
| --- | --- | --- |
| `diary_today` | 读某一天的日记（默认今天） | **只读**；输出明写「以上是用户自己写的原文，引用要逐字」 |
| `diary_append` | **追加**一条（类型 / 来源 / 正文） | 只追加：**永远不覆盖、不重排、不删**；回执给序号 / 字数 / 落盘路径 |
| `diary_update` | **原地改写**某一条（正文 / 时间 / 类型 / 来源） | 必须先 `diary_today` 拿到编号；**替换**而非新增；正文不能为空（要删就用 `diary_delete`） |
| `diary_delete` | 删掉某一条 | **不可撤销**；用户没说清是哪一条时，先把编号与内容念给他确认 |
| `diary_search` | 在所有日记里搜一句（跨天） | 子串匹配不分词；扫描天数有上限，触顶要说「更早的没看」 |

- ★ **不许用 `diary_append` 顶替改稿**。用户说「把这条改成…」「压成几条」时，追加一份改稿
  会让原文和改稿并排，第二天分不清哪条是原稿。合并 = `diary_update` 写合并后的那条，
  其余用 `diary_delete` 删掉。
- ★ **改写稿必须标明是「改写后的版本」**，不要和原文混在一起；引用用户写过的句子**逐字**，
  不要顺手润色。
- ★ **模型看不到私密日记**（0.31.0），而且这也是故意不给：`diary_search` 不传
  `includePrivate`（store 侧默认 `false`）、`diary_today` 读的是公开那半边、
  `diary_append` **没有 `vis` 参数**。边界就守在这三行上 —— 将来要「让 AI 也读私密」，
  那是一个需要单独想清楚、并由用户显式打开的决定，不该是一个默认值。
- ★ **空查询 ≠ 没有日记**。`diary_search` 收到空字符串时直接回「需要一个查询词」，
  而不是回「日记里一篇都没有」—— 后者是一句确定的假话，而用户无法分辨它和「真的没写过」。
- ★ 上下文与工具集**必须说同一件事**：`diaryContext()` 注入的那段 `<diary_context>`
  里写明了写入口有**三个**（`diary_append` 新增 / `diary_update` 原地改写 / `diary_delete` 删除）、
  改稿要先拿编号、删除不可撤销且含糊时先问、引用逐字、切片给了哪几条。
  ★ 0.36 之前这里写的是「只有 append、没有改写 / 删除」—— 工具改了而上下文没改，
  模型会以为自己在只能追加的旧世界里，于是拿 `diary_append` 去顶一次「改稿」。
  ⇒ **两边漂开时，症状不是报错，而是模型照旧世界行事。**
- ★ 切片后**序号必须还原成绝对下标**：一天超过 `DIARY_CONTEXT_ENTRY_COUNT`（8）条时
  只把光标附近那几条塞进上下文，如果序号从 0 重排，模型会照着假序号说话
  （「第 1 条」其实是一天里的第 5 条）—— 而 `diary_update` / `diary_delete` **就吃这个编号**，
  错的编号会改错行。
- ★ 正文由**宿主自己**从磁盘读，不接受客户端传进来的文本 —— 否则「引用」就变成了
  「客户端说什么模型就信什么」。
- ★ `diary_append` 的日期默认今天，但可以显式指定；**时间戳默认由宿主生成**（本地时区，
  `timeKey()`）。客户端与工具都**可以**传一个 `HH:MM`（补记某个时刻），但界面不传 ——
  跨时区写日记时，让两边各算一次必然对不上，而且那种错**不会报错**，只会把一条日记
  记到错误的时间上。

### 让 agent 读论文（`paper_*`，0.69.0）

论文那一半同样交出去，5 个工具。除导入外**只读本地库**，不联网检索：

| 工具 | 干什么 |
| --- | --- |
| `paper_list` | 列本地库，可按标签 / 状态（`new` / `reading` / `done`）/ 本地子串筛。返回的 id 给下面两个用。`hasFile: false` 表示只有元数据、没下到全文，打不开正文 |
| `paper_search` | 在**本地已存内容**里找词（标题 / 摘要 / 笔记 / 标签），返回命中片段。找**新**论文要用 `paper_import` |
| `paper_import` | 按 arXiv 编号 / 链接 / DOI / 标题导入一篇，默认顺手下开放获取 PDF；付费墙的会如实说「下不到」并让你自己传。已存在的合并，不重复 |
| `paper_abstract` | 不开 PDF 就能读一篇的元数据与摘要 —— 用来判相关性、做摘要、拼大纲 |
| `paper_related` | 按共享标签 / arXiv 分类 / venue / 作者，在**本地库**里找相关论文。它不是引文图，只用你自己的标签与元数据 |

**刻意没有 `paper_delete`**：删论文连 PDF 一起删、不可逆，不该由模型一句话触发 ——
回收站那条路留给你自己在界面上点。

### 时间窗的语义

- 相对写法（`3d` / `72h` / `2w` / `1mo`）以**调用时刻**往前推；`mo` 是 30 天，别和 `m`（分钟）混；
- 日期写法按 **UTC 零点**解释；`until` 给日期时**含整天** —— 否则「到 10 月 8 日」会把当天发的全漏掉；
- **没有发布时间的条目，设了窗口就一律排除**，并在输出里报出被排除了多少条。
  ★ 这一句必须出现：只说「命中 5 条」而不说「另有 12 条没有时间被排除」，模型会把缺失
  读成「就这么多」，于是给出一个建立在缺失数据上的、听起来完全确定的结论。

### 全文检索的闸门

正文散在 `subscriptions[].entries[].html`（feed 自带）与 `articles{}`（按需读过 / 抓过原文）两处，
单条平均 6 KB。100 个源 × 200 条的极端情况下，不设闸门就是一次调用把上百 MB 的 HTML
全转成纯文本。所以四个上限是显式写出来的（`src/host/search.js` 的 `SEARCH_LIMITS`）：

| 闸门 | 值 |
| --- | --- |
| 一次最多「看过」多少条目 | 5 000 |
| 一次最多把多少条正文转纯文本 | 800 |
| 单条正文最多取前多少字符 | 20 000 |
| 一次处理的正文总字符数 | 8 000 000 |

触顶时输出里会写「已达扫描上限，结果可能不全」—— 不许静默截断。

### Newsletter 内置目录

内置 18 个 AI 电子报源，**每一个都逐条真实请求测过**（HTTP 200 + 返回 XML + 至少 1 个条目）。
其中几条的地址和官网长得不一样，别照官网猜：

- **The Batch @ DeepLearning.AI** → `charonhub.deeplearning.ai/feed`
  （`deeplearning.ai/the-batch/` 下所有路径都是 404，首页 HTML 里 `rss` 出现 0 次）；
- **MIT Technology Review** → `technologyreview.com/topic/artificial-intelligence/feed`
  （The Algorithm 专栏没有独立 feed，只有 AI 主题源）；
- **Towards AI** → `newsletter.towardsai.net/feed`（Substack 自定义域）；
- **TLDR AI** → `tldr.tech/api/rss/ai`（API 路径；官网那个 `tldr.tech/ai/rss` 是 404）；
- **Daily Dose of DS** → `blog.dailydoseofds.com/feed`（同样是自定义域：它订阅页所在的
  `*.substack.com` 子域在本机取不到，别「顺手改回官网地址」）。

**2026-10-28 补的 9 条**（用户问「还有哪些常看的 AI Newsletter 你没收录」，对 24 个候选直连实测，
全部当轮有更新才收）：One Useful Thing（Ethan Mollick）、Interconnects（Nathan Lambert）、
AI Supremacy、Last Week in AI、AINews（smol.ai）、Ahead of AI（Sebastian Raschka）、
Simon Willison's Weblog、OpenAI News、Google DeepMind Blog。

★ 同轮**故意没收**的几个，理由不是「抓不到」而是「不值得占一行」：The Gradient 最新一篇停在
2026-02-18（八个月）、Lilian Weng 低频到四个月一篇、Alignment Forum 是讨论区不是电子报、
Pragmatic Engineer 不写 AI。**收一个停更的源，用户只会以为插件坏了** ——
所以这一轮给探针加了一条判据：取第一个条目的 `pubDate`，太旧的直接不收。

★ **「库里有」和「插件里能读到」是两件事**：上面每一条都是**直连**测的 ——
插件抓取不经过任何代理，借道能出去的通道测出来的 200 不算数。

**feed 里带不带正文，方向和你想的可能相反**，订阅前该知道：

| 源 | 列表里显示 | 点开之后 |
| --- | --- | --- |
| **Daily Dose of DS** | **全文**（插件解析后 20/20 条带正文，最长一条 5.08 万字符） | 无需再抓 —— 列表里就能读 |
| **TLDR AI** | 只有标题（20 条全无摘要） | **有全文** —— 现取 `tldr.tech/ai/<日期>`，实测 200、约 7300 字 |

没收录的源，原因记在 `src/data/newsletter-feeds.json` 的 `unavailable`，四类互不重叠：
**network** = 本机到不了（`*.substack.com` 整片被 DNS 污染 + TCP 阻断，连 Algorithmic Bridge /
Import AI / The Sequence / Data Machina / ChinAI 五条都落在这一类 —— 它们订阅页都在 Substack 上，
本机就是到不了；**这既不证明源坏了，也不证明插件取得到**）、
**blocked** = 应用层反爬（`superhuman.ai` 与 `aibreakfast.beehiiv.com` 都是 Cloudflare 托管挑战：
响应头 `cf-mitigated: challenge`、正文「Just a moment...」，四条路径 × 浏览器 UA 全 403，
而同域 DNS 可解析、443 可连）、
**partial** = feed 好但正文永远抓不到、
**no-feed** = 平台没开 feed（`newsletter.futurepedia.io` 是 beehiiv 但 `/feed` 全 404；
`every.to` 是 SPA；`bensbites.co` 的 `/feed` 与 `/feed.xml` 都返回 82 KB 的 Substack 首页 HTML）。

**The Neuron** 单列，因为它的结论在 2026-10-28 被**改判**了：原先记 `partial`（「feed 好、只是
文章页被 Cloudflare 拦」），复测发现整站都在挑战后面 —— `/rss/` 返回 403 + `cf-mitigated: challenge`，
`/feed` 与 `/rss` 直接连不上。也就是说**连 feed 本身都拿不到**，所以改判 `blocked`。
结论方向没变（照样摘除），变的是「为什么」—— 理由写错了，将来想恢复的人会照着错的方向查
（以为修好正文抓取就行，实际得先让 Cloudflare 放开 feed 路径）。

★ **「探不通」不等于「没有 feed」**。判据要三步：探 feed 路径 → 查 DNS 解析 → 测 TCP 连通性。
少了后两步，会把「被墙」误报成「这家不出 RSS」，方向完全错。

### 停更的会被裁掉：两条线，90 天标陈旧 / 365 天删除

两类目录**都进体检**（`src/data/catalog-health.json`），但删除线不一样：

| 目录 | 界面标签线 | 删除线 | 为什么不同 |
| --- | --- | --- | --- |
| 独立博客（404 条） | 90 天 | **90 天** | 从 upstream 目录同步来的，单价低；删错了还能按 `revision` 重新同步 |
| Newsletter（18 条） | 90 天 | **365 天** | 逐条实测**手写**出来的，没有 upstream ⇒ 删掉就是永久丢失 |

**2026-10-09 第一次对 Newsletter 应用删除线**，裁掉两条（都停在两年前）：

- **AI Valley** —— 最新一篇 2024-12-07（670 天）；
- **Grace Leung** —— 最新一篇 2024-10-11（727 天）。

两条的 feed 都是好的，被删的原因是**停更**，不是抓不到 —— 所以它们去了 `retired/`
（`retired/newsletter-feeds-retired.json`，带名字、地址、原字段与删除理由），
**没有**进 `unavailable`（后者记的是「当初就没收录」）。想恢复：把 `items` 里的条目
抄回 `src/data/newsletter-feeds.json` 的 `items`，顺手把 `verifiedAt` 改成当天。

> 裁剪 Newsletter 之前**必须先归档**：`prune-catalog.mjs` 会自动做这件事，
> 因为独立博客那半有 `revision` 可以兜底，Newsletter 这半没有。

**体检失败会重试一次**（2026-10-28 加）。不加的话「慢」会被记成「不通」：实测
`www.latent.space/feed` 有 **1.38 MB**、单次要 **7.7 秒**，`blog.google/rss` 要 10 秒以上，
而体检默认 12s 超时在并发 8 下必然把它们挤掉 ⇒ 快照记 `ok: false` ⇒ 界面上那行写「上次体检没抓到」。
用户读到的是「这个源坏了」，可它好端端的。加一次重试（间隔 800ms）之后同一轮从 16/18 变成 17/18。

> 仍有一条过不去：`latent.space` 在并发下两次 15s 都超时。它**不是死的** —— 单测 7.7 秒拿得到
> 1.38 MB 的 RSS。真要让快照也说它好，得把超时单独调大或串行跑；代价是体检变慢，暂时留着。
> 判据是「快照是快照」：`ok: false` 只说明**那一次没抓到**，界面文案本来就不说「已停更」。
